# 斯诺克 900：规则、计时与接入设计

日期：2026-11-02。状态：文档阶段已完成，用户随后授权实现；§1–10保留设计记录，后续确认与进度以§11为准。

本文面向后续实现与验收。架构扩展边界见 [architecture.md §4.7](architecture.md#47-斯诺克-900设计阶段2026-11-02)。经典规则现状见 [rules-v2-design.md](rules-v2-design.md)。900 是用户批准的新增规则集，不是 PCOL 原作转写。

## 1. 已确认的范围

| 项目 | 本轮要求 |
|---|---|
| 规则选择 | 用户可选择“经典斯诺克”或“斯诺克 900”，默认经典 |
| 首版入口 | 人机对战、双人规则测试；AI 与人类受同样的计时和判罚约束 |
| 900 玩法 | 15 分钟局时、20 秒出杆、碰库或进球要求、犯规后全台手中球、平分蓝球决胜 |
| 摆球 | 两个计时器都暂停；包括为本杆进行的合法手摆、系统复位及等待台面准备完成 |
| 球运动 | 出杆计时停止，整局时间继续消耗 |
| 出杆完成 | 杆头实际击中母球；按 Space、蓄力、启动动画均不算完成 |
| 压哨球 | 局时归零前已触球的一杆完整运行，结算全部得分和罚分后判断胜负 |
| 界面 | 展示本局剩余时间、当前出杆剩余时间、持杆方和暂停/运行状态 |
| 母球 | 900 使用红点外观，尺寸、质量及物理参数不变，红点随真实姿态旋转 |
| 经典与练习 | 保持既有规则、操作与外观；自由练习不施加 900 限时和判罚 |
| 本次交付 | 文档及必要架构说明，检查后提交推送，随后停止，等待实现指令 |

本轮不做桌面打包、联机服务器、登录、声音加工、球台几何或镜头算法修改。网页端继续作为当前交付入口；以后桌面版可复用游戏代码，不为此预建平台框架。

## 2. 依据与规则差异

### 2.1 来源及适用范围

1. [Snooker 900 官方玩法说明](https://snooker900.tv/learn-snooker-900)，访问于 2026-11-02：确认 900 秒、20 秒、犯规全台手中球、碰库要求、蓝球决胜；普通犯规说明为最低 4 分或更高的涉及球分值。网页是概述，不足以确定所有赛事边界。
2. [WPBSA 官方规则入口](https://www.wpbsa.com/rules/)与[2024–25 规则册](https://www.wpbsa.com/wp-content/uploads/2198_WPBSA-Rulebook-2024-25.pdf)：普通斯诺克细则及 Shoot Out 附录供对照；不能把 Shoot Out 的 10 分钟、15/10 秒或专门罚分直接移植为 900 的事实。
3. 用户在本次讨论中确认的计时、外观和入口约定，优先用于本项目；与赛事流程不同的部分明确登记。
4. `docs/spec/05-规则引擎.md`、`07-游戏流程.md`、`08-手中球D区.md`及现有实现，用于确定复用边界，不用于证明新增 900 规则。

900 的全台手中球是允许摆放母球，不是把任意彩球提名成当前目标的“自由球”。仍按红/彩交替及最后依次清彩进行，彩球意图提名与自由球提名必须区分。

### 2.2 本项目明确采用的约定

- 摆球期间局时与出杆时限均暂停，摆球完成后恢复；不是宣传为赛事原样计时。
- 截止前已经触球的杆完整结算，包含犯规和压哨进球，不在归零时冻结物理或立即按旧比分判胜。
- 红点母球是外观选择，不是换用中八/九球的尺寸、质量或摩擦参数。
- 普通赛事中由裁判控制的准备和计时阶段，游戏必须由核心状态明确表达，不能交给 UI 是否显示来决定。

### 2.3 实现前必须核实的细则

以下是证据缺口，不是可以省略的功能；相关规则未定稿前不编码猜测，也不能将部分实现标成“完整官规”。

| 项目 | 已知情况与后续动作 |
|---|---|
| 超时/未碰库罚分 | 900 网页只明确普通罚分概述；Shoot Out 附录第 16–17 条对此有最低 5 分规定。需找到 900 的适用条款，不能直接套经典最低 4 分或 Shoot Out 最低 5 分；还需明确彩球待提名时的罚值 |
| 蓝球决胜完整程序 | 900 网页确认蓝球决胜，未说明摆位、先手选择、每次尝试时限与犯规处理；须补赛事依据 |
| 蓝球对照依据 | Shoot Out 第 14 条为蓝球原点、母球 D 区、同等尝试次数后比较、直接进球要求及先手选择。仅作核实清单，不自动成为 900 的规则 |
| 提前清台/末黑犯规平分 | 核实 900 是否同样转蓝球决胜；不能误入经典的非开球方争黑分支 |
| 碰库细节 | 核实首碰前碰库、贴库打离、袋角弧面是否满足义务；实际几何标记与规则概念需逐项对应 |
| 特殊不可击达局面 | 官网概述不设自由球；全台手中球仍无法合法触及时如何处理须核实，不继承经典自由球菜单作为暗中兜底 |
| 首杆及终场边界 | 记录官网简介与实际赛事的起表时刻差异；先手/首杆时限及同一时刻双归零优先级需在实现前定稿 |

优先查赛事官方详细说明或官方比赛裁判示例；如果只能找到 Shoot Out 对照条款，则将拟采用的游戏约定提交用户确认，并记录来源不足。既有“非开球方争黑”授权只适用于经典，不扩展为蓝球先手授权。

| `src/controller/shot-controller.ts` | 动画开始发 `sim/shooting-start`，稍后才调用 `stroke`；拒绝触球直接抛错 | 区分预备与实际触球；超时拒绝是正常取消流程，清动画和预备状态 |

| `src/controller/ai-runner.ts` | 有搜索、思考与出杆延迟，同一动画通道 | 搜索和延迟计时，迟到结果作废，不绕开实际触球检查 |
| `src/app-game.ts` | UI 预检硬接经典 Ref；回放会提前返回；球停后仍等起身再判分 | 摆球预检由当前规则提供；计时不能绑相机结束，也不能被回放隐式暂停 |

`game.ts`与`app-game.ts`应按职责拆出计时、900 裁决与装配文件，不能把全部分支追加到已有大文件。单个源文件继续不超过 400 行。

## 4. 选择入口与生命周期

规则类型与对局方式是两个维度。建议新局区增加“规则：经典斯诺克 / 斯诺克 900”，人机与双人测试共享；自由练习隐藏或禁用规则选择。

- 下拉改变是下一局配置，不立即修改正在进行的对局；开始新局/加载球局后才生效。
- 默认经典；进入 900 后显示双计时器及红点母球，切回经典恢复经典显示。
- 双人测试继续受 DEV 与 `VITE_RULES_TEST=0` 控制；正式构建可以包含 900 人机，不能包含双人测试菜单。
- 完整重置恢复已加载的规则类型、预设、比分、球权与初始计时，清空压哨标志、决胜轮次、动画、旧判罚和回放；不得采用尚未加载的下拉值。
- 普通新局沿用既有正式开球轮换，测试预设不消耗正式序列；蓝球决胜先手另按核实后的规定处理。
- 核心不能用 `practice + 900` 暗中开启计时；具体拒绝或归一化行为随配置契约冻结。

## 5. 计时状态与事件顺序

### 5.1 两个计时器

本表描述逻辑阶段，不要求新增同名 `GAME_STATE` 值。

| 阶段 | 整局计时 | 出杆计时 | 行为 |
|---|---|---|---|
| 新局装配、系统归位 | 暂停 | 暂停 | 初始值 900 秒和 20 秒；不在资源加载时扣时间 |
| 本杆合法手摆及确认前 | 暂停 | 暂停 | 界面显示摆球暂停；人类与 AI 一致 |
| 摆球确认、可瞄准/提名/思考 | 运行 | 运行 | 当前合法杆首次启动为 20 秒 |
| 蓄力、后拉、尚未触球动画 | 运行 | 运行 | 预备成功不锁定出杆资格 |
| 已接受的实际触球、球仍运动 | 运行 | 停止 | 同一杆只接受一次 |
| 球停后的规则结算、系统复位 | 暂停 | 暂停 | 完成后进入下一杆，不能等相机起身来决定计时 |
| 局时归零但有已触球的杆 | 固定 0 | 停止 | 禁止新杆，等待本杆完整结算 |
| 终局 | 停止 | 停止 | 无后续超时或自动罚分 |
| 蓝球决胜 | 正常局时固定 0 | 待规则核实 | 独立轮次，不重开 15 分钟，不套经典争黑 |

下一杆无手摆时，在台面归位完成且游戏允许操作后开始计时；必须确保 UI/控制器的激活不会额外扣掉玩家无法操作的时间。已经允许操作后的走位、提名、瞄准、AI 思考均消耗出杆时间。

首杆建议在初始摆球确认且允许操作后一起开始两个计时器，以统一用户确认的“摆球完成后恢复”约定；与赛事首次触球起局表是否不同，列入 §2.3 核实记录。

### 5.2 摆球暂停必须有权限

- 只有核心授予手中球权限且处于合法摆球阶段，才暂停两个计时器；任意打开菜单、提示框或按 P 不能暂停。
- 需要明确“确认摆球”动作。无有效位置不能确认；系统已经给出合法位置时也应允许确认采用原位置。
- 后续若在仍有手中球权限时再次摆球，暂停并保留已用时间；确认后恢复剩余时间，绝不重新获得 20 秒。新一杆才重置出杆计时。
- 预备出杆后不允许再摆；假放置、非法位置、重复确认与越权操作不能改变时间。
- 本轮不增加摆球倒计时；未来联机的离席处理独立设计，不暗中推翻本次双暂停约定。

### 5.3 独立于帧率、物理与回放的时间

- 核心接受装配根提供的单调时间数值，测试使用可控时钟；核心不读 DOM、系统墙上时间或 `setTimeout`。
- 比赛时长不能用物理 `evolution`、快进次数或回放倍率计算；一次归位调用多次 `step(0.1)` 不意味着消耗同样的比赛时间。
- 装配根在命令和物理触球边界更新计时，不只在绘制 HUD 时更新。帧率降低或长帧不能额外送时间。
- 同帧内跨越触球、出杆截止和局时截止，按逻辑时刻先后处理；不能先扣整帧时间，再把本已提前触球的杆误判超时，也不能按 Space 时刻回填触球。
- 900 活跃对局建议暂不开放现有暂停式回放，终局后仍可看上一杆及 ¼ 慢放；经典和练习不变。这是防止现有回放提前返回造成停表的接入建议，需随实现方案确认。
- 切标签页/窗口失焦不自动成为暂停理由；恢复时先同步已流逝时间和裁决，再放行输入。不得把休眠的几十秒作为一个巨大物理步硬塞给求解器；触球附近的后台恢复须有专项测试。

### 5.4 超时和压哨结算

出杆截止前未真实触球，产生一次超时裁决；取消待触球动画、预备意图和 AI 旧任务，不施加冲量。禁止把“未实际出杆”当作无首碰的空杆再罚一次。具体罚值依 §2.3 核实结果。

收到有效触球时锁定本杆身份并停止出杆表。随后局时归零只锁住新杆；继续真实物理、正常音效和轨迹记录，待所有球停止后一次性计算进球、犯规和比分，再选择终局或蓝球决胜。

最终比分优先于界面动作：压哨进球可能追平，压哨犯规可能使领先者落后；不能按归零瞬间的旧比分弹出胜负。已在归零前结束的超时裁决仍须入账。

边界提案：触球时刻严格早于截止才合法，恰好截止按到期处理；局表与出杆表同时到期且未触球时优先终局、不重复添加时间犯规。此优先级须与 §2.3 一并定稿并写成测试，不能由回调注册顺序决定。

## 6. 900 裁决与摆球

### 6.1 与经典规则的组合

复用目标顺序、合法首碰、贴球、提名、一般犯规分值计算及彩球归位基础；900 单独管理碰库义务、时间犯规、全台手中球及决胜。

900 的正常犯规处理为一次计罚、结束当前单杆、对方获得全台手中球。常规流程不进入经典的自由球提名、让对方继续或 Miss 原位重打菜单；极端例外按 §2.3 核实结果补齐。

多个违规原因可以合并描述，但不能简单累加所有罚值。先汇总本杆违规与判罚，再提交分数、球权、目标推进和归位；避免新增碰库犯规后仍保留先前错误的连杆/阶段变化。

### 6.2 碰库证据

`ShotResult`目前没有碰库记录，`ContactEvent.isSS=false`也可能包含皮头或其他静态接触；声音的 `ImpactEvent`会过滤不播放的碰库，不能作为规则依据。

在模拟器的真实接触观察路径累计独立规则证据，经过规则定义确认的库面/袋角才计入；台呢、袋底、漏斗不作为普通碰库。必须覆盖实际求解器能看到而旧回调可能遗漏的持续接触。

证据只读、与声音是否开启无关；`predict`不能写入真实杆证据，`stroke/reset/restore`清理边界明确。观察不修改求解、CCD、冲量、休眠或积分。若规则只需本杆布尔值就不存无用轨迹；需要接触顺序时再按已核实细则最小扩展。

贴库初始静止接触不能直接当成已经完成碰库义务。母球或目标球有效碰库均须覆盖；进袋不豁免错误首碰或母球摔袋等其他犯规。

### 6.3 全台手中球

放置区域是球台内合法支撑区域，不是含袋口的整个包围矩形。校验球半径、库面/袋口边界、与其他球间距及有效高度，复用现有几何能力，不由 UI 自行裁判。

核心最终校验与控制器绿色预览使用同一规则能力。不能只删除 UI 的 D 区限制，也不能把经典 `SnookerRef` 全局改成全台；开局、犯规后与决胜可能具有不同放置区域。

AI 获得同样的合法放置权，通过同一个放置/确认命令使用。可先采用有限候选位置与现有路线评分，不要求第一版求全台最优，但不能永远绕过摆球流程或沿用 D 区限制。

### 6.4 蓝球决胜

单独保存决胜阶段、轮次、每位尝试结果和胜者。正常比赛分数保持原值，决胜结果独立显示；不能伪造加 5 分来复用按总分比较的 `winnerIndex`。

具体摆位、先手、同等尝试次数、超时/犯规和翻库处理依 §2.3 补齐。现有 `finished`依赖 `ballOn===0`、`winnerIndex`依赖总分大小，需要扩展语义，不能因常规比分相等而永远返回无胜者。

## 7. 分层与接口准备

本节描述所需能力，架构契约以 `architecture.md §4.7`为准；尚未核实的规则不冻结为公开签名。

| 层 | 职责与接口方向 |
|---|---|
| core 对局装配 | 接收规则配置与外部时间，管理钟表、球权、一次性裁决及决胜；输出复制的只读状态 |
| core/rules | 900 规则策略、罚分与摆放区域；通过结构接口消费模拟器证据，不反向依赖 GameSession |
| core/simulator | 提供真实碰库只读证据；保持旧 ShotResult、SerialData、物理公式 |
| controller | 摆球确认、触球时刻、超时取消；经装配回调请求核心，不自己计罚 |
| ui | 只显示计时快照、规则选项与提示；无独立权威倒计时，无内部核心引用 |
| render | 红点外观及既有姿态显示，不读取或修改规则状态 |
| app 装配 | 时间来源、选项接线、控制器/AI 激活、HUD 更新和材质选择 |
| devtools | 注入双 USER、预设与测试时间配置；调用正式规则，生产构建排除 |

建议最小扩展为 `GameOptions.ruleset`、对局只读计时/阶段快照、时间推进命令、合法摆放查询与摆球确认，以及模拟器碰库证据。具体名称、时间单位、枚举、犯规码和兼容默认值在规则核实完成后写入架构签名表，再编码。

现有 `stroke`的布尔失败结果可复用；重点是所有调用方对超时失败都进行正常清理。不要为 UI 计时每帧广播完整球台，也不要复用 `sim/shooting-start`作为实际触球或停表事件。

对局状态通过装配根复制值/注入回调交给 UI；如果需要新增 EventBus 事件，先在架构事件表写明载荷。表现层仍不横向 import，规则与 AI 不依赖 DOM/网络。

## 8. 界面与红点母球

- 双计时放在比分牌附近，避开瞄准中心和底部回放控件，经典/练习不显示倒计时。
- 局时以分秒显示，出杆时限可在最后数秒显示十分之一秒；具体排版是实现选择，判罚使用未舍入时间。
- 明确标识当前玩家，以及“摆球暂停”“球运动中”“等待本杆结算”“蓝球决胜”；不能让冻结的数字看起来像故障。
- 临时超时/犯规提示沿用限时与 × 关闭；关闭不撤销罚分。常驻计时器和必要确认按钮不自动消失。
- 文案使用单一语言，不把中英文并排混写；沿用现有英文犯规提示，文本集中管理供后续语言切换。
- 红点使用球体局部坐标或球面 UV，不能贴在世界坐标或屏幕上；首版建议六个红点，不改变反射与球体轮廓。
- 用现有旋转姿态验证高杆、低杆、侧旋及滑动阶段；不能由位移推算假滚动，否则低杆与滑移会显示错误。
- 回放和进度定位直接使用已录制的四元数；切换规则或重置不能污染其他球的共享材质。
- AI 球权继续自由旁观，本地玩家出杆才启用 V 三模式；不改相机位置、焦点平滑或起身参数。
