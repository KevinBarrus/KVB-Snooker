# 内测经典联机：部署接线与人工验收

本文件补充第三步的部署接线，不替代 [身份部署](../deploy/README.md)。账号、PostgreSQL和登录由该文档维护；玩法与范围见 [可玩经典联机](multiplayer-playable-design.md)。

## 1. 两个服务、一个公开来源

浏览器只使用同一个 HTTPS 来源：

- `/api/auth/*`、`/api/health`：身份服务。
- `/api/rooms`、`/api/rooms/*`：房间服务的 HTTP 接口。
- `/net`：房间服务的 WebSocket，代理必须支持 Upgrade。
- `/api/internal/*`：公网明确返回404，不能转发。
- 其他路径：前端静态构建/身份服务。

身份与房间服务通过内网 `POST /api/internal/session/verify` 通信。两边配置同一个受控 `INTERNAL_TOKEN`；不要写入 Git、浏览器构建变量或网址。房间服务不直接连接 PostgreSQL，账号停用、退出或改密后，后续命令/心跳校验会断开旧会话。身份不可用也不能回退到开发令牌。

## 2. 房间服务配置

| 环境变量 | 用途 |
|---|---|
| `PUBLIC_ORIGIN` | 必填，浏览器实际访问来源，例如 `https://snk.example.com`，不带路径/末尾斜线；须与身份服务一致 |
| `INTERNAL_TOKEN` | 必填，与身份服务一致；由受控环境文件加载 |
| `IDENTITY_URL` | 身份服务内网来源，默认 `http://127.0.0.1:8788`；容器网络可用 `http://identity:8788` |
| `COOKIE_NAME` | 可选，默认 `snk_session`，两服务须一致 |
| `NET_HOST` | 默认 `127.0.0.1`；容器内可设 `0.0.0.0`，容器端口不要暴露公网 |
| `NET_PORT` | 默认 `8787` |

本轮协议升级到v7，发布时需要同步更新前端与房间服务，旧页面须刷新。

开发机先准备现有资产。身份服务启动时必须配置 INTERNAL_TOKEN。房间服务在仓库根目录执行：

```sh
npm run net:players
```

上面的环境变量应已通过受控环境文件或终端环境加载。本命令编译并启动已认证入口；原 `npm run net:server` 是开发令牌入口，不能拿它当公网服务器。两者默认使用同一端口；切换前停止旧开发服务，不能同时占用8787。

Vite已分别代理 `/api/rooms` 与 `/net` 到 `127.0.0.1:8787`，其余 `/api` 沿用身份服务代理。可用 `NET_PROXY` 覆盖房间内网地址；`IDENTITY_PROXY` 仍由身份单元维护。PUBLIC_ORIGIN必须等于真实Vite来源（例如 `http://127.0.0.1:5173`），不能混用 localhost 与127.0.0.1。

## 3. 生产交接给部署负责人

现有身份-only部署包不会自动带上房间服务，发布前必须完成以下接线：

1. 同一版本执行 `npm run build`、`npm run identity:build`、`npx tsc -p tsconfig.server.json`。
2. 运行包除已有内容外，加入 `.cache/net-server/`。房间进程工作目录为包根目录，必须能读取 `public/assets/physics/table.json`；可以仅复制这一个物理文件到对应路径（前端dist/assets中的副本不自动等于该路径）。原始资产仍不入Git。
3. 创建独立房间进程，命令为 `node .cache/net-server/server/player-main.js`，注入上表配置；不复用开发入口。停止/启动由部署服务管理器负责。
4. 在已有Caddy路由中，将下面处理器置于静态/身份的兜底代理之前，内部端点屏蔽仍保留。原生部署用 `127.0.0.1:8787`，容器部署用房间服务名。

```caddyfile
@game path /net /api/rooms /api/rooms/*
handle @game {
    reverse_proxy 127.0.0.1:8787
}
```

5. 发布前确认两个真实账号均能登录、建立WSS连接和完成一杆。`GET /health` 是房间进程的内网存活检查；它不能证明身份数据库或所有外网链路可用。

当前房间、当前比赛仍只在单个房间进程内存中；进程重启会丢失。应在两位内测者都不在对局时更新。没有跨进程路由/持久化之前不要启动多个房间实例做随机负载均衡。身份数据库持久化不等于比赛已存档。

## 4. 玩家怎么验收

使用两个不同浏览器资料或无痕窗口，以两个不同账号登录：

1. 主菜单选择“双人对战”。A选择经典赛制及局数，创建房间，把显示的六码交给B。B输入该码加入；输错码显示不存在，不能自动创建。
2. 双方页面加载完成，各点“准备”。只一方准备时，不能出杆。首局服务器随机开球，后续交替开球。
3. 当状态提示本机回合，按W瞄准、Space出杆；力度条只对本人瞄准显示。对手能看见球杆入位与击打，自己的相机仍可自由观察。
4. 两端均有比分、罚分、单杆与球声；网络调试面板默认隐藏。开发排查才使用 `?debug=1`。
5. 获得手中球时可以摆球，落点由服务器校验；再次按P可重摆，W进入瞄准。确认非法点不能推进比分或球权。彩球自动/手动提名、自由球以及犯规接手/让对手继续/Miss复位使用同一套核心规则。
6. 请求暂停必须由对方同意；双方“准备继续”后倒计时恢复。可以同时点准备，不要求先后顺序。
7. 三局两胜可用“认输本局”快速检查：每局结束双方准备下一局；开球轮换、局分累积；整场结果仅产生一次。整场结束后可离开房间，再创建下一场。
8. 刷新页面重新登录时，同一服务器进程会识别原成员席位；同账号第二窗口不能挤占当前连接。此能力尚不是120秒重连裁决、服务器故障恢复或长期暂存。

自动验收：先准备真实资产和正式构建，使用独立测试数据库连接运行 `TEST_DATABASE_URL=<测试库连接> npm run test:players`。脚本创建并清理独立schema，不清空已有表；执行真实登录、创建/加入/准备、双窗口击球/声音/比分、暂停、换局与整场退出。旧 `npm run test:net` 保留延迟、丢确认、显示同步与相机专项。

## 5. 本轮边界

只开放经典联机；联机900、语音、协商重摆、长期暂存、掉线判负和统计上榜不由本单元冒充完成。正式首局随机；浏览器自动验收为复现问题固定首局开球方，不改变产品配置。单机练习和人机仍使用原入口。
