## 2. 本次修订取代哪些旧假设

| 旧文档或行为 | 本次确认的修订 |
|---|---|
| 900 连续摆球路径约束 | 与原作一致，只验证最终落点，不允许重叠；不沿台面绕障 |
| 放球后一直显示绿色光环 | 成功放置后隐藏，仍有资格时按 P 重开 |
| pointerdown 同时提交放球和启动拖动 | 区分完整点击与拖动，台外拖动不能落球 |
| 900 永远不可暂停的旧假设 | 增加双方同意、遮挡台面的正式暂停；菜单和摆球依然不停表 |
| 旧扩展规划的游客练习或简单昵称身份 | 游客只可经典 Easy；正式账号邮箱登录，游客无持久成绩 |
| 仅保留上一杆即可提供高光库 | 需要逐杆归档和长期存储，复用片段内容，不额外剪等待 |
| 命令加种子必然跨版本逐位复现 | 必须验证；正式状态由服务端裁决，长期播放保留版本和轨迹 |
| 双人测试或菜单房间入口等同真实联机 | 开发工具与占位 UI 不代表网络、账号和存档已经完成 |
| 一局结束就增加胜场 | 胜场指整场，实际胜局另外统计 |
| 本地缓存以后补传即可上榜 | 第一版要求在线，离线可信度与同步另行设计 |

原作复刻证据保留，不改写历史源码事实。新增联网、权限、暂停和收藏行为属于本项目扩展；原作没有的部分不得编造 PCOL 行号作为依据。

## 3. 推荐施工顺序

### 单元 A：摆球修复

独立修复当前用户已验收发现的交互问题，不等待服务端。经典、900、人机、双人规则测试均回归，镜头算法和用户调好的物理参数不动。通过后单独提交推送并人工验收。

### 单元 B：整场与生命周期基础

补齐整场与单局的边界、可序列化的完整状态、暂停/恢复以及统计事件时间。先在本机人机和测试环境验证长局制、900、待处理判罚、重摆和恢复。暂停要真正停止适用的物理、AI 与出杆流程，不能只有一个按钮。

这一阶段只实现可复用对局能力，不把正式账号、数据库连接或 WebSocket 导入 core。

### 单元 C：账号、数据库与访客入口

建设稳定用户身份、邮箱登录、游客权限、资料及迁移管理。确定服务端目录与 API 契约，准备大陆测试部署。先验证两名用户独立登录及权限，再接入对局，不用浏览器 localStorage 冒充身份系统。

### 单元 D：权威双人房间

先做邀请、双方准备、席位、经典一局对局和唯一终局，再扩展长局制与 900。所有正式命令走同一服务端校验，补齐球运动、自转、计时、规则选择和旁观镜头。用不同设备及网络验收。

### 单元 E：暂存、重摆、重连与故障

完成双方协商、持久化检查点、120 秒重连、无期限暂存与版本兼容。针对重复请求、断网、服务器重启、计时截止竞争和正在发生的一杆做故障测试，不只检查正常路径。

### 单元 F：成绩与排行榜

使用前面已记录的权威事件生成八类 W/L、胜局、得分杆率、平均出杆时间、破百及 147。验证重新计算和事务重试不重复计数，再公开榜单；先采集必要事件，不能等做榜单时才发现缺少历史触球时间。

### 单元 G：高光库与语音

高光先实现每杆可靠归档和手动收藏，再实现自动破百/147、连续拼接、公开与回收站。录制基础要提前接入，不能等整场结束后补造缺失片段。语音作为独立交付单元，失败不阻塞比赛。

高光与语音可按内测反馈调整先后，不与出杆修复绑成一个大提交。MP4 导出、离线成绩同步、Steam 身份和跨区域部署留到后续。

## 4. 施工纪律

- 每个单元保持可回归，不把多个领域塞进一个文件或一次提交。
- TS strict、禁 any、单文件不超过 400 行、遵守已有依赖方向。
- 改公开接口先同步架构契约；改模块同步该目录 AGENTS.md 的状态，完整需求留在这些设计文档。
- 每单元通过 `npm run test` 与 `npm run typecheck` 后提交推送；交互和联机另做对应浏览器、双客户端和故障验收。
- 不提交 analysis、原始媒体、生成资产、密钥和本机缓存；不夹带其他模型尚未完成的工作。
- 保存已有经典、人机、摄像机、音效和物理调参验收基线，不借联机重构改变手感。

## 5. 未冻结的实施参数

这组文档已足够开始摆球与基础能力施工，但没有替用户拍板所有上线政策。暂停具体配额、昵称唯一性、长局制双人首局选先、媒体容量、异常双离线裁决等，在相关单元施工前逐项给出默认建议并确认。文中标为“建议”的内容不得宣称用户已批准，更不得冒充官方斯诺克或 900 规则。

没有必要现在要求用户选择数据库表名、消息字段名或对象存储厂商；这些由工程实现提出可审查方案。费用、账号凭证及实际部署授权到准备好具体方案时再处理。
