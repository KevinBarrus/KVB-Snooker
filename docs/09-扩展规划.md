# KVB-Snooker 扩展规划（Extensions Roadmap）

> 依据：2026-10-17 需求对齐会议。每项含"现状 / 设计 / 架构埋点"。埋点分两类：
> **【现在做】**= 复刻（M1-M3）阶段就要落的基础设施；**【后续阶段】**= M4+ 再实施。
> 对应产物文档：规则细节 → `08-手中球D区.md`、`05-规则引擎.md`、`07-游戏流程.md`。

## 0. 横切基建【现在做】

### 0.1 可播种 RNG（一切确定性的前提）

现状：AI 误差注入/选路乱杆/结算随机点均用 `Math.random`（`1.chunk.js` L2672-2744 等）。
决策：core 层全部随机改走 **种子化 RNG 接口**（如 xorshift，种子进：存档 / 网络命令帧 / 回放文件）。
影响三处变现：5 回看重演、4 精彩时刻、3 网络同步与反作弊。成本现在为零，以后重写代价极高。

### 0.2 比赛录制的"确定性重演"格式【现在做】

一杆/一局的持久化 = `初始 SerialData 快照 + 击球命令序列（StrokeVars + RNG 种子游标）`。
回放 = 从快照重演（物理逐位一致，见 01 §4.4 determinism）。存储极小（KB 级），任意长度。
以下 4/5 两项均构建在此格式上。

## 1. 规则完善（WPBSA 官规）【后续阶段：规则层 v2】

现状（与作者 README 一致）：free ball 无、miss/再打一杆无、touching ball 无、彩球报色无。

### 1.1 touching ball（贴球判定）
撞击后若母球停在与 ball-on 球接触位置 → 下杆不得推球/不得不打开角度。物理层已有接触信息（`touchPresolveHandler`，01 §4.3），规则层需持久化"贴球对"到 gContext 并在 checkResult 与摆球合法性中消费。
实现参数：接触判定半径 `球A半径+球B半径+ε`，复用 `touchBalls`（05 §4）。

### 1.2 free ball（自由球）
foul-and-a-miss 后若被做斯诺克于所有 ball-on → 对方可宣布自由球：
- 宣布后 `gContext.ballOn` 置哨兵（设计：引入 `-1` 或复用 65535 变体），任意球可作目标
- 进袋/计分按"等效 ball-on 分值"（红球局中打彩球=红球分值等，官方规则）
复用点：65535 哨兵机制（05 §6）已证明"任意 ballOn"可达；等效分值在 checkResult 加分支。

### 1.3 miss 罚则与"重解"（foul and a miss）
foul 且未尽力击中 → 判 miss，对方三选（1b 决议已定）：
- a. 复位让对手重打（**需恢复原局面**：foul 前按规则应回滚到对方杆前快照 + 已进袋球复位——依赖 0.2 快照，回滚 = restore 前一杆前 SerialData）
- b. 对手从当前位置打
- c. 让对方接手（自己打）→ 进 free ball 判定
加参数判定"尽力"：官方本可主观看线路，游戏里简化为不做主观判定（AI 或规则自动判 miss），后续可加开关。

### 1.4 报色提名（nomination）【已定，2026-10-17】

强制选色场景（决议）：
- **free ball 激活时**——官方规则要求提名等效 ball-on 球
- **当前应当打彩球、但母球看不到完整目标彩球时**——防止首触合法性争议
- 其余场景不强制、不上 ML；数据层增加 `gContext.nominatedBallOn`
- ※ 具体选色 UI 形态（何时弹出/交互方式）另行讨论后再定稿

## 2. 让杆（frame conceded）与多局赛制【后续阶段：流程层 v2】

### 2.1 手动让杆
玩家 concede 按钮 + 二次确认 → 流程层直接推进到下一 frame（不需打到 ballOn 终态）。计入玩家 penalty/损失。

### 2.2 AI 自动认输（2a 决议：按难度分级）
- 基线阈值：AI 落后分差 > { easy: 8, normal: 12, hard: 20 } 时 conceding
- 精细化（2a 议定方向）：以"**名义剩余分 vs 现实可得分**"动态计算——
  `剩余分 = 台面球分和`；`现实可得分 ≈ 剩余分 + 每颗彩球复位重打的潜力（粉黑居后、黑球加塞成斯诺克送 free ball 的极端预期）`。
  草案公式：`concedeIf (对方分 − 我方分) > 剩余分 + 情景修正×难度系数`；粉黑残局、`发球斯诺克+free ball` 场景单独修正。
  每档系数做成可调参数，首版只实现基线阈值，精细化后补。

### 2.3 多局赛制（2b 决议）
支持局数序列：`1（一局决胜）/ 5-3 / 7-4 / 9-5 / 11-6 / 17-9 / 19-10 / 25-13 / 33-17 / 35-18`（与职业斯诺克赛制一致，mode = 最多局数，先到 ceil(n/2) 胜）。
新增"比赛"层状态机：`match: { format, framesWon: [user, ai], frameIndex }`——**比赛状态不进物理存档**，与 frame 内 SerialData 分离。
存档（2b 关注点）：每 frame 结束滚动保存 `{比赛状态 + 当前 frame SerialData}`；中途退出可续打（resume list）。

## 3. 网络对战（PvP）【后续阶段：P3】

### 3.1 架构建议（3a/3c：服务器权威——**待拍板**，见文末待拍板清单）
- server 复用 `packages/core`（TS 零 DOM 物理与规则）做权威模拟
- 玩家客户端只发**命令**：`{type:'stroke', vars, rngCursor}` / `{type:'respot', pos}` / `{type:'concede'}`
- 服务器广播：场地状态摘要 + 关键事件（触球/进袋/出界，驱动音效与 UI）
- 拉取式细节：双方在各自客户端本地重演（0.2 格式）——带宽每杆几百字节
- 同步不依赖回合计时器丢帧（3b 现状说明：**计时器=每杆限时防挂机**，是否启用见文末待议 3）
- 栈：**Node + WebSocket + PostgreSQL**（TypeScript monorepo：`packages/core` 共享 / `apps/web` / `apps/server`）。不引 NestJS 等重框架，用轻量框架（如 Fastify + ws）起步。

### 3.2 匹配（3b 决议）
大厅匹配池（按 region/delay 可后加）+ **好友邀请**（好友在线列表 + 邀请入房）。房间 = 一次性 frame 容器，与 AI 局互不相干。

## 4. 账号与生涯数据【后续阶段：P3，与 §3 同栈】

- **注册**：全球唯一 nickname + 密码（ bcrypt/argon2 存哈希），后续可绑定邮箱
- **游客**：可玩 practice / single play（含 AI），不可进 PvP
- **统计落库**：`玩家生涯 { 胜率(按比赛), framesWon, maxBreak(L至最高), centuries 破百数, maximums 147 数, fouls, 出杆精度 }`——记账在 server 端（防客户端篡改）
- **精彩时刻**：
  - 单杆：玩家手动标记（回看 Ui 上加"存为精彩"），存 = 0.2 格式片段（击球命令 + 初始快照）
  - 破百/147：**自动**捕获——server/流程层检测 break 跨 100 / 147 达成，把"该次 break 期间每杆"的命令序列连成一个回放条目
  - **呈现形态（已定）**：破百/147 = 每颗球的片段**连成连续回放序列**（逐杆自动衔接、与回看一致镜头），不做 mp4 编码；未来需要真视频时再加离线导出
  - **公开分享**：条目 → 公开/私密标记；排行榜按 break 分值/147 数/标记次数
  - **他人观战（已定）**：仅"查看他人公开分享的精彩时刻回放"；实时观战正在进行的比赛——暂不做，等用户量起来后再扩展（P4+）

## 5. 回看全长化【复刻阶段就该修（M3 前）】

现状：球轨录 500 帧@60fps≈8.3 秒录满冻结（`new us(500,60)`，L7416），多库杆被截断。
决议（5a/5b）：**确定性重演替代定长录像**——回看时从快照 + 命令序列重演实时渲染，长度无上限、逐帧一致、零额外存储。
镜头：与现版一致"跟母球"（复用 movieClip cam track 与 follow 逻辑，04 §6）。
实现次序建议：M3 内完成（与 audio 同期，均依赖 touchPresolve 事件钩子）。

## 6. 优先级排序（建议）

```
P0 复刻（M1-M3）内含：0.1 播种 RNG、0.2 录制格式、5 回看重演改造

P4 运营型：排行榜/分享/观战/102颗粒度打磨
```
