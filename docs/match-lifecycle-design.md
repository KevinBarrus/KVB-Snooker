# 比赛生命周期：暂停、暂存、重摆和恢复

状态：2026-11-10 更新。暂停/继续已接入本地练习、经典/900人机、单机双人规则测试及经典联机开发原型；暂存、协商重摆、掉线恢复与正式联机900仍待后续单元。其余待决参数统一见项目状态。本文只定义状态转换与玩家权限，不定义数据库或网络实现。

## 1. 区分操作

| 操作 | 含义 | 正式联机权限 |
|---|---|---|
| 展开菜单 | 查看操作，不改变比赛进程 | 本人操作；对手和时钟继续 |
| 暂停 | 短时间冻结，稍后继续同一状态 | 双方同意 |
| 暂存 | 保存未完成的整场，离开后再共同恢复 | 双方同意，不设置保存期限 |
| 重摆 | 放弃本局当前尝试，重新摆标准开局 | 发起请求，对手同意才执行 |
| Miss 复位 | 根据规则恢复上一杆球位并保留罚分 | 规则授予的选择，不是重摆 |
| 认输 | 按明确的局或整场范围结算 | 本人确认，界面写清范围 |

练习和人机暂停不需要另一名真实用户同意；AI 自动接受适用的暂停或暂存。游客不提供长期暂存。双人规则测试继续拥有开发重置能力，不把它暴露给正式联机玩家。

## 2. 暂停与 900 时钟

900 摆球、菜单、切后台不暂停任何计时。真正触球停止本杆 20 秒；球运动期间局时继续；全部静止、结算和必要归位完成后开始下一杆。正式暂停是用户批准的独立例外，两表在暂停生效期间冻结。

联机暂停请求发出后比赛照常继续。对方接受后在安全边界生效：不截断已经发生的击球，等待运动和结算完成。若此前已经超时或终局，不能用晚到的接受请求撤销结果。

暂停时双方用不透明遮罩覆盖台面，不展示球位、辅助线、回放或可用于继续观察的缩略图。暂停前已知信息无法抹去，但不能继续借暂停操作台面。恢复后清掉旧输入，避免按住鼠标或 Space 的残留动作触发。

2026-11-09 用户确认：900 每位玩家每局可发起一次已生效暂停，最长 180 秒；被拒绝或撤回的请求不消费次数。到达上限或双方提前准备，统一倒计时 3 秒恢复。经典和练习不限制暂停次数与时长；联机仍须双方同意。重摆不刷新本局暂停预算，新一局才重置。

提前继续需要双方准备；到达有限暂停上限按约定自动恢复，并给出短暂倒计时。恢复不重置本杆 20 秒，也不补偿暂停前已经消耗的时间。倒计时一旦开始不可撤回或由一方反复触发续时。

### 2.1 当前入口与验收

本地自由练习、预设练习和人机：菜单 → 暂停；人机自动同意。自建球形练习沿用[已确认的菜单约束](my-shapes-design.md)，不新增暂停按钮。单机双人规则测试仍由同一操作者控制两席，因此一个暂停/继续按钮代为确认双方，不冒充真实联机协商。

联机开发入口：请求暂停 → 对手同意或拒绝；发起者可在接受前撤回。暂停后两端分别点击“准备继续”，随后统一倒计时。请求本身不限制对手当前击球，已确认预备杆也要完整执行。未生效时任一连接离开会撤销请求；已暂停时不能单方面继续，有限上限触发的自动继续不受准备状态影响。正式120秒掉线宽限属于后续单元。

遮罩首次聚焦容器，防止先前的 Space 误触“准备继续”；Tab 可到按钮，Esc 不绕过协商恢复。恢复保留视角，不重新激活相机或刷新出杆时长。暂停不是长期暂存：关闭两个开发窗口或重启服务器仍不会自动找回比赛。

协议已升级为v6，验收前重启 `npm run net:server` 并刷新双方网页。自动验收入口为 `npm run test:pause`，另运行原有 `test:net`、`test:controller` 回归。

## 3. 暂存与恢复

双方同意暂存后，等待正在发生的一杆完成并裁决，在稳定边界保存状态；请求本身不冻结时钟。保存成功后才离开对局。保存失败应明确显示，不能先显示“已保存”再丢失比赛。

暂存不设置到期日，恢复时仍是原来两名玩家、原规则、局数、比分和剩余时间。双方准备后继续，不新开一局、不重新抽先手、不刷新 900 时间或暂停次数。长时间离开不计入有效比赛和单杆用时。

关闭浏览器不等于双方同意暂存；主动退出时应提供暂存请求或明确认输，不把单方面离开变成无限期冻结比赛。返回菜单也不应偷偷删除仍进行中的比赛。

旧存档不能依靠“当前最新版应该差不多”恢复。保存规则、引擎及物理配置版本，保留兼容运行版本，或提供经过验证的迁移。不可兼容时明确报告，不篡改球位、时钟和成绩来凑合恢复。

## 4. 联机重摆

只重摆当前局，保留前面已完成的局及整场局分。保持当前局序号和本局开球方，不把重摆当作下一局轮换开球。请求期间照常运行，双方接受且到达安全边界才执行。

当前尝试的台面、分数和单杆清空，生成新的本局尝试标识；被放弃尝试保留审计记录，但不贡献正式排行榜成绩。已发布的统计必须能撤销对应贡献，不能只减分而留下破百数。

900 重摆保留已经消耗的整局时间；新尝试准备好时获得一杆正常出杆时间，不把局时恢复为 15 分钟。若局时在执行前已经耗尽，应先按终局规则结算。

旧回合的出杆、提名、判罚请求和客户端动画失效。历史高光可保留实际回放内容，但应标明来自已重摆的尝试，不能冒充正式计入成绩的破百。

## 5. 掉线与服务端故障

玩家掉线有 120 秒重连宽限，900 比赛计时继续。重连后以服务端状态为准，不恢复掉线前客户端剩余时间。超过宽限判掉线方整场负；若比赛已因局时耗尽等正常规则提前结束，只结算一次。

正式暂停与重连宽限是不同计时器。已经生效的暂停按暂停规则处理比赛时钟，但不无限延长失联席位的重连宽限。单方面掉线不能自动取得暂停权。

服务器故障单独处理，不能把服务端不可用伪装成某名玩家掉线并判负。建议采用技术中断状态，从最后可恢复记录继续，排除服务器不可用期间的计时；责任不明或双方同时失联的争议状态应保留证据，不能任意给某一方增加胜场。此类尚未定稿的异常政策见 [D06](project-status.md#待确认的产品决定)，实施后需要故障演练验证。

## 6. 实现边界

保存字段、命令确认、统计幂等、时钟恢复和版本迁移统一见 [持久化设计](match-persistence-design.md)；连接恢复与消息去重见 [协议设计](multiplayer-protocol-design.md)。恢复必须满足本文件行为，不能以数据库实现方便为由改变暂停、重摆或判罚。

## 7. 验收

- 展开菜单不会暂停 AI 或对手；正式暂停确实冻结适用状态并遮住台面。
- 请求未接受时继续计时；暂停接受与超时竞争时结果唯一。
- 双方暂存、关闭、隔日恢复后，规则选项、球位、自转和时间一致。
- 重摆只影响当前尝试，不改变已完成局分、开球轮换和 900 已耗局时。
- 在命令确认、运动中、结算和写统计时模拟故障，不重复执行或重复计数。
- 120 秒重连期限和 900 终局竞争时只产生一个整场结果。
- 服务端故障不会自动记成玩家负场；旧版本存档有可验证恢复路径。
